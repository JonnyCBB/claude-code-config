# Maintain a verification skill

A feature map rots the moment the service changes, and a rotted map is worse than none — it is a
confident lie that a reviewer will trust. This is the upkeep loop for a skill generated by
`/jbb-feature-dev:create-verification-skill`, or any project-local skill with a feature map.

**The unit of rigour is the feature, not the sentence.** Cover every feature file from source and
exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — one PR ships proven doc, harness or map corrections.
- **blocked** — coverage could not finish, or a proven fix could not ship safely. Say exactly what
  blocked it.

## Edit scope

**Only edit the verification skill's own directory** — its `SKILL.md`, `features/`, and any harness
scripts it owns.

**Never edit product code during a run.** Behaviour the map describes that the service no longer
does is either doc drift (fix the map) or a product regression (report it — do not paper over it in
docs).

## The pass

**0. Locate the target.** Find the project-local skill with launch/drive sections and a feature map
(usually `.claude/skills/verify-*/`). Several candidates → ask which. None → stop and point at
`/jbb-feature-dev:create-verification-skill` rather than inventing a target.

**1. Index hygiene.** Read the feature map README and glob its siblings. Fix missing, extra,
duplicate or dead entries. Lightweight; no generated inventory.

**2. Source wave.** One read-only agent per feature file, launched concurrently in a single message.
Each answers "how does this feature actually work?" from source, flags likely doc drift **with
citations**, and returns one concise live-verification recipe.

Children never drive the service and never edit files. Return shape: feature summary / source entry
points / likely drift or none / one recipe.

**3. Reconcile.** Every feature file must have a returned summary — a missing one is a coverage
hole, not a pass. Merge overlapping recipes into as few service states as practical. Spot-check
cited drift; do not re-prove clean claims. Sweep recent churn for user-facing surfaces missing from
the map, and require a concrete source path before calling one missing.

**4. Live pass — required even when source looks clean.** The coordinator owns all driving. Follow
the verification skill's own Launch section: one long-lived instance driven serially for services,
a fresh isolated run per drive for short-lived jobs. That skill decides, not this one.

Exercise every feature at least once, holding three invariants whatever fails:

1. **Never drive an instance you have not health-checked since it last did something surprising.**
   Doctor before the first drive, on each fresh session where sessions are the unit, and again
   after any failed drive. Where doctor cannot see the failure — a wedged state on a healthy
   process — reset or relaunch rather than hoping.
2. **Evidence captured so far survives every cleanup**, checked at its named location, not assumed.
3. **Nothing a drive started outlives that drive's usefulness.** Failed-iteration residue is cleaned
   whether the session is stuck, exited or shared. For a shared instance, clean the residue, not the
   instance.

A doctor failure caused by skill drift **is** drift: fix it under edit scope and retry once —
restarting only what the fix invalidated — before calling the pass `blocked`.

A feature that cannot be reached is `verified-unreachable` **only with the concrete prerequisite**
(auth, entitlement, environment, external state) and the route attempted. If the map omits that
prerequisite, that is drift.

Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the
last drive of the run, including those re-proofs — evidence stays, per the skill.

**5. Triage.**

| Finding | Disposition |
| --- | --- |
| Wrong or missing caller-POV description | Doc drift — fix it |
| Working behaviour the harness cannot drive | Harness gap — fix it, scripts executable and invocation documented |
| Service behaviour that is actually broken | **Product gap** — record it for the user, keep it out of this PR |

**6. Ship or stop.** For `changed`: one PR of proven corrections, re-reading every changed file
first. For `clean` or `blocked`: no PR — report the outcome and the coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a
scratch location. Do not commit them.

## Why the maintenance half is not optional

`/create-verification-skill` produces a snapshot. Without this loop the map keeps asserting
behaviour the service stopped having, and the first person to trust it is the one who least
deserves to be misled — someone verifying a change they did not write.
